## Що реалізовано

1. `Value` зберігає значення, градієнт, батьків і локальне правило похідної.
2. Додавання, множення, стала степінь і ReLU будують граф. Для навчання додано sigmoid і чисельно стабільний softplus.
3. `backward()` будує топологічний порядок без рекурсії, очищує градієнти, задає вихідний градієнт 1 і накопичує внески через `+=`. Повторний виклик обчислює свіжі градієнти. Тест `x*x+x` перевіряє повторне використання вузла.
4. Градієнти `((a*b+c)**2).relu().sum()` порівнюються з PyTorch float64 і центральними різницями з кроком 1e-6. Для скаляра `sum()` повертає сам вузол. Перевірка охоплює три набори входів.
5. Модель 2→8→1 використовує ReLU в прихованому шарі та sigmoid на виході. BCE обчислюється як `softplus(z)-y*z`, що математично еквівалентно BCE від sigmoid, але стійкіше чисельно. Дані: make_moons, 200 точок, noise=0.15, seed=42; 150 для навчання та 50 для тесту. Навчання: 300 епох, повний пакет, SGD, lr=0.1. Час включає forward, loss, backward, оновлення ваг і запис loss; підготовка даних та оцінювання виключені. Обидві реалізації використовують float64 і ті самі ваги. Наведено медіану п'яти запусків на CPU з одним потоком PyTorch.
6. Для дозволеної альтернативи компіляції використано `torch.jit.trace`. Окремо вимірюється побудова trace; steady-state inference вимірюється після 30 прогрівних викликів, без autograd, медіана п'яти серій по 500 викликів. Граф autograd обстежується через `grad_fn.next_functions`, а граф tracing зберігається у текстовому файлі.

## Пояснення

Ланцюгове правило передає градієнт виходу до батьків. Наприклад, для `u=a*b` внески становлять `du/da=b` та `du/db=a`. Якщо вузол використано кілька разів, внески з усіх шляхів додаються. Зворотний топологічний порядок гарантує, що перед обробкою вузла вже зібрано внески його нащадків. Для ReLU у нулі прийнято похідну 0, як у PyTorch.

Скалярний рушій створює Python-об'єкт для кожної операції та кожної точки. PyTorch виконує обчислення всього пакета в оптимізованих тензорних операціях, тому це порівняння демонструє також користь векторизації, а не лише різницю механізмів autograd.

Tracing фіксує операції для прикладу входу. У цій моделі немає залежних від даних Python-розгалужень. Для моделей із такими розгалуженнями trace може відобразити тільки шлях, виконаний під час трасування. Tracing і `torch.compile` мають різні можливості; результати цього експерименту стосуються саме tracing.

Зменшення Python overhead допомагає при багатьох повторних викликах, особливо для малих операцій. Час підготовки має окупитися: якщо eager займає E секунд на виклик, trace T, а підготовка C, поріг приблизно `C/(E-T)` викликів за умови E>T. Для коротких запусків чи операцій, де домінує матричне ядро, виграш може бути малим або відсутнім.

Транспонування створює view без копіювання, змінюючи strides. У тесті порівнюються `view @ weight` та `view.contiguous() @ weight` з однаковими значеннями і розмірами 512×512; копіювання винесено за межі основного вимірювання й оцінено окремо. Транспонований тензор не обов'язково повільніший: матричні бібліотеки можуть ефективно підтримувати такий layout. Висновок не можна переносити на всі несуцільні зрізи та всі операції.
